# 账号健康、轮换与额度刷新

## 基本原则

轮换池只能选择已启用且经过验证的健康账号。失败后的时间冷却与恢复健康是两件事：冷却到期只表示允许再次探测，不代表账号已经恢复。

正常请求一旦开始向客户端输出流式内容，就不能换 Key 重放，以免产生重复输出或重复计费。

## 失败隔离和恢复探测

账号遇到额度耗尽、限流、鉴权失败、网络失败或上游异常后，应退出正常轮换池，并记录：

- `last_check_status`
- `last_check_at`
- `last_error`
- `next_probe_at`

目标状态如下：

| 状态 | 含义 | 是否参与轮换 |
| --- | --- | --- |
| `healthy` | 最近一次探测成功 | 是 |
| `quarantined` | 已失败，尚未到复测时间 | 否 |
| `probe_due` | 已到复测时间，尚未验证 | 否 |
| `probing` | 正在执行恢复探测 | 否 |

恢复流程：

1. 失败账号至少隔离 10 分钟。
2. 到达 `next_probe_at` 后，执行最多输出 1 个 Token 的连通性测试。
3. 探测成功才清除错误并恢复为 `healthy`。
4. 探测失败则更新失败原因，并把下一次探测时间继续延后至少 10 分钟。
5. 同一账号同一时间只能有一个恢复探测。
6. 正常用户请求不能被当作恢复探测。
7. 没有健康账号时，可以立即探测已经到复测时间的账号；全部失败时返回“无可用账号”。

该行为由 [Issue #1](https://github.com/kyui-azusa/kimi-switch/issues/1) 跟踪。当前版本尚未完全实现，不能把现有的冷却到期行为视为最终约定。

## 额度刷新周期

额度刷新周期按账号的固定时间轴连续滚动，不应因为本地请求、Token 消耗或最后使用时间而重新起算。

建议为每个账号保存：

- `quota_cycle_anchor_at`：可靠的周期锚点；
- `quota_cycle_seconds`：周期长度；
- `next_refresh_at`：当前时间之后最近的周期边界；
- `refresh_source`：数据来源；
- `refresh_observed_at`：最近一次确认时间。

下一次刷新时间按以下规则推算：

```text
next_refresh_at = anchor + n × cycle
```

其中 `next_refresh_at` 必须是当前时间之后最近的一次周期边界。

## 锚点来源和可信度

导入账号时应尝试从 Kimi 配置或官方响应元数据中获取明确的刷新时间。连通性测试、额度耗尽响应或 `Retry-After` 信息也可以用于更新观察记录。

仅有导入时间时，只能把 `imported_at` 记为观察时间，不能把它直接显示成精确刷新时间。没有可靠自动来源时，应允许用户手动校准一次刷新时间和周期。

界面应区分：

- 官方响应或配置提供；
- 本地观察推算；
- 用户手动校准；
- 尚未知晓。

到达预计刷新时间后，只触发恢复探测；账号仍需探测成功，才能重新加入轮换池。

该功能由 [Issue #2](https://github.com/kyui-azusa/kimi-switch/issues/2) 跟踪。
